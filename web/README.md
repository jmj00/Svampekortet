# web

Mobile-first PWA client: a MapLibre map of Denmark with Danish address search
(DAWA), an observation layer per species, a species detail sheet (photos,
seasonality, safety note), and the conditions model (the geometric mean of
habitat × seasonality × weather — see `../docs/adr/0006-v0-probability-model.md`
and `0008-geometric-mean-score-combine.md`) surfaced two ways:

- a **conditions card** in the detail sheet, scoring the dropped pin for that
  species, and on the map the **named forests within 10 km of the pin coloured
  by their score** for that species, in four classes (0–29, 30–59, 60–79,
  80+); a tap in a coloured forest gives its name and score
  (`forestscores.ts`, `../docs/adr/0021-forests-coloured-by-score-replace-the-conditions-grid.md`);
- the species list **ranked by conditions at the pin** the moment a pin is set
  (tap the map, pick an address, or use "locate me").

An **"Om Svampekortet"** panel (button under the species list) explains what the
0–100 number is and is not, carries the safety note and the Giftlinjen number,
and lists the data sources and dataset version.

## Start screen

A fresh visit opens on the start screen ("forside", `src/start.ts`): four ways
in, each landing in the main interface already set up for the task. It is a
layer of the same page (`data-start` on `#app`), not a route. The wordmark, the
mark in the phone's address field and the house button beside the Svampe/Skove
switch all reopen it.

- **Skip it with `?kort`** (e.g. `http://localhost:5173/?kort`): straight to the
  map, for links and for browser checks that start from a fresh profile.
- A visitor who set a pin last time goes straight to the map with that pin
  restored. The pin is the only thing the start screen stores:
  `localStorage["svampekortet.pin"]` = `{"lon":…,"lat":…,"label":…}`, written
  when a pin is set and removed when it is cleared (`src/startstate.ts`). The
  About dialog's "Privatliv" section says so.
- With a pin set, the two cards that need a place go straight in for it and
  offer "Skift sted"; the place step's search lists named forests (from the
  forest payload) above the addresses.
- Everything on it comes from the manifest (species, photos, what is in season
  this month); nothing is hard-coded.

## Forests

`public/data/forests.json` holds one point per named forest; the outlines are
in `public/data/forest-outlines-<n>.json`, one band of the country per file,
listed in the manifest's `forest_outlines`. The app fetches the band a pin
falls in when the pin is set (`src/forestoutlines.ts`), never with the first
paint.

- **The forest at the pin** (`forestAtPin` in `src/forests.ts`, used by the
  location chip and the Skove tab alike) is the smallest forest whose outline
  contains the pin, else the nearest outline edge within 125 m, else none.
  Without outlines (a manifest with `forest_outlines` null or missing, or a
  band that could not be fetched) it is the nearest forest point within
  1.5 km, as before.
- The outline of that forest is drawn on the map (`src/forestshape.ts`).
- Background and measured sizes:
  [ADR-0020](../docs/adr/0020-forest-outlines-for-the-pin.md).

## Error monitoring

`src/sentry.ts` initialises `@sentry/browser` **only when `VITE_SENTRY_DSN` is
set** (CI, via a GitHub Actions variable), so `npm run dev` and PR builds send
nothing. Errors only — no tracing, no session replay. Third-party / network noise
is filtered, and `beforeSend` strips query strings so a typed address never
leaves the browser. Source maps upload to Sentry during the deploy build when
`SENTRY_AUTH_TOKEN` is present (`vite.config.ts`); the upload is non-fatal.

## Run

Needs Node.js 22 LTS (ships with `npm`). Install via `winget install OpenJS.NodeJS.LTS`
or the MSI from <https://nodejs.org>, then open a fresh terminal.

```sh
npm install
npm run dev          # http://localhost:5173
npm run lint
npm run test         # vitest: score.ts / forests.ts / keywords.ts ... (pure logic)
npm run build        # tsc --noEmit && vite build
npm run icons        # regenerate PNG app icons from favicon.svg
```

## Data

The app reads a static payload from `VITE_DATA_BASE` (default `/data`, i.e.
`public/data/` in dev). At deploy the workflow copies `build/publish/` there.

`public/data/` holds a committed **sample** payload for local development:

- `manifest.json` + `species/<slug>.json` — the species index (with each species' monthly
  season and a thumbnail URL, enough to draw the list rows) and the detail docs
- `model/manifest.json`, `model/<slug>.json`, `model/current.json` — the
  conditions model, regenerated by `python scripts/gen_sample_model.py` after a
  `python -m pipeline.model.fit --out build/publish` run

The sample docs are heavily downsampled, so dev scores are illustrative, not real.

`src/score.ts` is a line-for-line port of `pipeline/model/`; the Python side
carries the tests.

## Offline

`public/sw.js` is a hand-rolled service worker (registered in production only, by
`src/register-sw.ts`). After the first online visit the app shell, the JS/CSS
bundle and the data payload are cached, so the species list, conditions scores
and species info work with no signal. Map **tiles are not cached** (cross-origin,
large, OSM tile policy) — offline the map has no fresh imagery.

The shell (`index.html`) and the `/data/` payload are **network-first** (with the
browser HTTP cache bypassed), so a deploy's new bundle and data land on the next
online visit rather than one visit late; the cache is the offline fallback. The
content-hashed build assets are cache-first. Bump `CACHE` in `sw.js` if the cache
ever needs a hard reset.

## Basemap and address search

Both work out of the box in a reduced form: the map falls back to OpenStreetMap
tiles, and the address search box returns nothing. For the real "Skærmkort"
basemap and address search (Adressevælgeren), copy `.env.example` to
`.env.local` and set `VITE_DATAFORDELER_API_KEY` — a plain API-Key (not an
OAuth Shared Secret) from an IT-system in Datafordeler Administration
(<https://portal.datafordeler.dk/hjem>).
